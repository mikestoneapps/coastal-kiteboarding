Phased so the live page never breaks and each phase ships something the rider notices. Each phase is one or two Claude Code sessions. Prompts to paste are at the end of each phase.

## Phase 1 — Station readings for every spot (hourly job)
Goal: "Wind measured now" works for all 15 spots, including the buoy-only ones, without the browser calling NOAA.
- Add `.github/workflows/observations.yml`: runs `obs_standalone.py` every hour 05:00–21:00 Pacific, commits `obs.json` to `main` (use the built-in `GITHUB_TOKEN`; the workflow needs `contents: write`).
- `index.html`: on load, fetch `obs.json` (same origin) **in addition to** the direct NWS calls; prefer the fresher reading per station. Keep the direct NWS calls so the page works even if the job is late.
- Show age honestly: "32 min ago"; grey the tile if older than 2 h.
- Also fetch the station's wave height from buoys (`wvht_ft`) and show it beside the marine forecast when present.

Prompt: *"Read CLAUDE.md and SPEC.md. Implement Phase 1 of docs/BUILD-PLAN.md: an hourly GitHub Actions workflow that runs obs_standalone.py and commits obs.json, and make index.html read obs.json alongside its direct NWS fetches. Run the script once locally to generate a first obs.json and commit it. Test the page in a headless browser before opening the PR."*

Status (2026-10-15): built. `obs.json` was committed empty because the build container's network policy blocks api.weather.gov and ndbc.noaa.gov; the first run of the **Station observations** workflow on `main` (hourly, or Actions → Run workflow) fills it. Until then the page behaves exactly as before, on its direct NWS calls. A reading's age is computed from its own timestamp, so a late job shows "3h ago" greyed rather than a frozen "12 min ago".

## Phase 2 — Settings that follow him, and "Keep this spot"
Goal: rider profile, comfort limits, per-spot overrides, checklist edits and alert settings persist across devices.
- Smallest honest option: a tiny backend (Cloudflare Worker + KV, or Supabase free tier) with magic-link email login. No passwords.
- Migrate existing localStorage (`goc.settings`) up on first login; keep localStorage as the offline cache.
- Add "Keep this spot" for discovered/added spots (Phase 4 uses it).

Status (2026-10-15): built. Backend is a Cloudflare Worker + KV (`sync/worker.js`, free tier, never pauses) with a **device-link** login instead of a magic-link email: the first device generates a random sync key, "Link another device" shares a link carrying it, no mail sender or domain needed. The page works unchanged with sync off; `docs/SETUP-SYNC.md` has the no-terminal dashboard steps, and `.github/workflows/sync-worker.yml` deploys automatically once Cloudflare secrets exist. `goc.settings` migrates forward (gains `updatedAt`, `kept`); `goc.cache` and the daily `goc.check.*` ticks stay local. Conflicts resolve newest-wins via the Worker's 409. "Add a spot" (shipped as "Keep a spot that isn't listed", renamed 2026-10-16) lives under the list: a place found by name (Nominatim, the Elsewhere geocoder) or the phone's location, coordinates shown read-only with a Check-on-map link and an Edit fallback, and which way the beach faces → direction sectors (onshore ±30° best, ±80° works, reverse ±50° offshore), estimated drive times, forecast in the same batched call, `k-` ids. The Worker is not deployed yet: the rider (or whoever sets up the gift) follows SETUP-SYNC.md once.

## Phase 3 — Alerts and the weekly outlook
Goal: SPEC §8. One push digest per refresh run; Sunday 6 pm email.
- Hourly job (extend Phase 1's workflow or a second one) that pulls forecasts for all spots, scores them server-side with `scoring.js` (run under Node) using each user's saved parameters, and decides what to send. Web Push (VAPID) for the PWA; email via a free-tier sender (Resend/Postmark) for the outlook.
- Store "already alerted (spot, day, score)" so nothing repeats.
- Add the Alerts sheet's "Enable notifications" button to the page (push subscription), replacing the mock.

Status (2026-10-15): **push built; the weekly email is the next PR.** The `alerts` job in `.github/workflows/observations.yml` (same hourly schedule, runs beside the observations job) runs `alerts/run.mjs` under Node: it asks the sync Worker for every rider with a push subscription (identified by the Phase 2 sync key, so alert settings and the "already alerted" list are per rider, not per device), pulls one batched Open-Meteo forecast for the curated spots plus everyone's kept spots, scores with `scoring.js` using each rider's style, factor weights, comfort limits and per-spot overrides, and sends one Web Push digest per rider (`web-push`, VAPID). `scoring.js` gained the comfort limits and `minHours` window the page already applied, and `alerts/test.mjs` evaluates the page's inline scoring block against it so the two can't drift again. The Worker (`sync/worker.js`) stores subscriptions (`p:`), alert state (`a:`) and serves the VAPID public key; admin routes for the job are behind an `ADMIN_TOKEN` secret. `sw.js` only shows notifications (no fetch handler, no cache). Setup is in `docs/SETUP-SYNC.md` under "Push alerts"; until the secrets exist the job skips itself. Not done: the Sunday email, station blending in the job (same-day alerts are forecast-only), SMS.

## Phase 4 — Away-from-home mode
Goal: SPEC §5. When outside the home region, discover spots within the drive radius (OpenStreetMap kitesurf/windsurf tags + named beaches), score them from a batched Open-Meteo call, infer direction sectors from coastline orientation, mark rows "auto", and let him Keep them. Photos and webcams enrich in the background (Wikimedia Commons geosearch; standard thumbnail widths; descriptive User-Agent).
- Verify OSM coverage in 3 US regions before relying on it; fall back to named beaches.

Status (2026-10-16): **built; the spot list is precomputed.** Live testing showed the public Overpass servers are too slow and unreliable to query from the browser (30+ s answers, mirrors down or rate-limiting), so the spot search no longer touches Overpass at runtime. A weekly GitHub Actions job (`.github/workflows/away-spots.yml`, Mondays, `away_spots.py`, Python, mirrors overpass-api.de, kumi.systems, private.coffee and mail.ru) fetches every `sport=kitesurfing/kiteboarding/windsurfing` feature worldwide (one query, 15-minute read timeout, two tries per mirror; 902 elements in 66 s on the first live run) plus the named `natural=beach` features of the US, Canada and Mexico in about 4°×4° bounding-box tiles over the coasts and Great Lakes only (47 tiles, `TILES` in the script: Pacific from the BC north coast to Oaxaca with the Sea of Cortez, Gulf of Mexico, Atlantic from the Keys to Newfoundland, the Great Lakes, Hawaii; 90 s server timeout each, one try per mirror, a 3 s pause between tiles, an 80-minute budget for the whole beach phase) and commits a compact `away-spots.json` (id, name, lat, lon and only the tags `osmNotes` reads; one spot per line). The first live run proved the tiles necessary: the single country-wide beach query (US) got 502/504/500 from all four mirrors. The run is partial-tolerant: the file is written whenever the sport query succeeded, a tile that fails on every mirror is logged and the previous file's beaches inside it are carried over, and the job exits non-zero only when the sport query itself failed; it prints the final counts (sport spots, beaches, failed tiles) at the end. The build container can't reach Overpass, so **the first catalogue run happens on GitHub**: open Actions → "Away spots catalogue" → Run workflow once after merging; until then the page shows "No spots found here yet" when away (the file is missing), which is the same banner as a genuinely empty area. Tests: `python3 away/test_away_spots.py` (the catalogue job against the mock Overpass answers in `away/fixtures.mjs`, with the network faked: tile coverage, failed-tile carry-over, exit codes, counts), `node away/test.mjs` (the page's block under Node with a mock catalogue) and `node away/browser-test.mjs` (headless Chromium; the catalogue is served from the fixture, `--real-file` uses the repo's own; `BASELINE_DIR` compares home mode with `main`'s page, identical). Still open: look at the real rows for "San Diego", "Hatteras NC" and "Hood Canal" once the catalogue exists, and check the file size on the phone (a few MB is expected; it is cached in localStorage for 7 days, or refetched if the quota refuses it).

How it works: more than 150 mi from both houses (GPS, a typed place name via Nominatim, or pasted coordinates) the page fetches `away-spots.json` once (same origin, cached in `goc.awayspots` with a date for 7 days), filters it to the drive radius (minutes → road miles ÷ 1.35, 30–120 mi straight-line); every sport-tagged spot is kept, named beaches fill up to 40, duplicates within 0.75 mi collapse (a tagged launch beats the beach it sits on). The list renders at once with names, distances and neutral tiles, then one batched Open-Meteo call (plus marine) scores them; that is all the score waits for. Everything else is background enrichment with a 60 s budget each and never blocks: the shoreline within 2.5 km of each spot (Overpass; the list re-sorts once when it lands, and if it fails the spot simply stays "auto, facing unknown"), webcams, photos. Facing comes from the nearest shoreline: OSM `natural=coastline` ways run with the water on the right, so the beach faces the segment's right-hand normal; for `natural=water` closed ways (lakes, rivers) the water is on the side of the polygon's centre, and such spots get no surf forecast. The sectors are the same rule kept spots use (onshore ±30° best, ±80° works, reverse ±50° offshore). No shoreline within 1.6 mi → direction isn't scored (every direction "works", nothing gates) and the detail says so; Keep then opens the sheet so he picks the facing. Rows are marked **auto**; the list re-sorts once when scores land. Webcams come from OSM `man_made=surveillance` + `surveillance:type=webcam` nodes with a link within 8 mi; photos from Wikimedia Commons geosearch (1 km, landscape, free licence, 640 px), three at a time, patched into the tile without re-sorting. Results are cached per area (`goc.cache.away`, 7 days) so reopening is instant; "Search again" clears it. Keep this spot saves it into `settings.kept` (synced by Phase 2) with the inferred rules, OSM id, cam and photo, and copies the forecast so no refetch is needed. Nothing found or Overpass down → a clear banner with "Add a spot by hand" (the Phase 2 keep sheet: name + coordinates + facing) and "Search again". Home mode (either house, or Elsewhere within 150 mi) runs exactly the code it did before; `allSpots()` only grows in away mode.

Not done: wind stations for discovered/kept spots (the detail says "not looked up yet"); the Windfinder/Windy/surf-forecast cam indexes (no free API; OSM cams only); the Oregon-specific checklist hints are skipped for discovered spots.

Status (2026-10-16, photos and the add buttons): the single "Add a spot" button under the list became two: **Look up a new spot** (the sheet in name-search mode) and **This spot is killer** (the same sheet with the coordinates already filled from the phone's location and the cursor in the name field; if location is refused the sheet says so and shows the place search). The rider can attach his own photo to any spot, curated or added: **Use my photo** in the spot detail opens the camera/photo picker, the page resizes to 480×320 JPEG (about 40 KB, quality stepped down until it fits) and caches it in IndexedDB (`goc.photos`, keyed by spot id); with sync on it is uploaded to the Worker (`PUT/GET/DELETE /v1/photo/<spotId>`, sync-key auth, 100 KB limit, KV key `ph:<rider hash>:<spotId>`) and `settings.photos` (spotId → taken at) tells other devices which photos to fetch in the background. The tile prefers the rider's photo over the built-in or Commons one; **Remove photo** restores the default everywhere. Spots added at home now get the same background Commons lookup as away-mode spots (scored picker, no photo unless something scores positive, `photoChecked` remembers an answer). Kept spots that arrive from another device get their forecast fetched at once instead of at the next full refresh. Tile layout on narrow phones: tiles have a minimum height, the text column has 10 px of vertical padding so the status chip always clears the bottom edge when the name or conditions wrap, and the photo stretches to the tile's height. The add-spot sheet (both buttons) also has **Add a photo**: the same picker and resize, a thumbnail of the exact tile image, and on Save the photo is stored under the new spot's id (IndexedDB, `settings.photos`, Worker upload when sync is on) so the tile shows it from its first paint; it stays optional, and Use my photo in the detail still changes it later. Tests: `node sync/test.mjs` (photo routes), `node away/browser-test.mjs` (390 px layout with a long name, both add buttons, the GPS sheet, the photo round trip on two devices through a mocked Worker, adding a spot with a photo). The Worker must be re-pasted in the dashboard (SETUP-SYNC.md).

## Phase 5 — Polish
Forecast accuracy memory and per-spot bias (SPEC "Add soon after" #7), seasonal context, two-spot compare, post-session feedback, native iOS wrapper for a home-screen widget if push proves unreliable.

Groundwork (2026-10-19, forecast honesty PR): the page and the alert job now fetch five Open-Meteo models in the one call and score the hourly **median of best match, ECMWF and NBM** (`consensus()` in `scoring.js` and the page's scoring block, parity-tested by `alerts/test.mjs`); all five vote on "Models agree / mixed / disagree" and the spot detail shows the spread ("Models: 11–19 kn (NBM highest)"). Every wind figure carries its unit and the Rider sheet has a knots / mph switch (`settings.units`, display only, synced). The hourly observations job also runs `accuracy.py`, which appends one line per spot with a fresh station reading to `accuracy.jsonl` (observed knots beside each model's forecast for that hour, 90-day window; `python3 test_accuracy.py`). The five-model call falls back to the old three-model call if the API ever rejects a model id, so the page keeps working either way; the build container cannot reach Open-Meteo, so the first real five-model answer is seen on GitHub Pages and in the first Actions run after merge.

**Next, after ~4 weeks of `accuracy.jsonl` (mid-November 2026):** compute per-spot, per-model bias from the file (mean signed error and mean absolute error of each of `bm/ecmwf/nbm/gfs/icon` and of `median` against `obs`, per spot, for readings from stations within 10 mi; the Tillamook stations are 8–20 mi from the beaches they stand in for, so expect a systematic under-read there and weight by distance). Then apply it: subtract each model's bias per spot before the median, show "Usually reads N kn high here" in the detail, and consider dropping a model from the median at spots where it is consistently worst. Keep the page free of any new fetch for this: the job can commit a small `bias.json` the page reads same-origin, like `obs.json`.
